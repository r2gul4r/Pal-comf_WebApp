## 2026-07-25 — pak 인덱스와 선택 추출 검증

### 목표

설치된 팰월드 1.0 pak 전체를 풀지 않고 핵심 DataTable과 한국어 자산의 실제 경로를 확인한다.

### 내가 AI에 준 요청

팰월드 1.0 설치 데이터를 기준으로 거점 작업 특성·파트너 스킬 역검색기를 구현하도록 요청했다.

### AI가 제안한 내용

- 먼저 `repak`으로 pak 인덱스를 읽는다.
- 알려진 DataTable 경로는 후보로만 사용하고 현재 pak에서 다시 찾는다.
- 핵심 `uasset`과 `uexp`만 선택 추출한다.

### 내가 의심하거나 검증한 부분

- 예전 버전에서 알려진 `DT_PalMonsterParameter`와 `DT_PalCharacterIconDataTable` 경로가 현재 1.0에도 존재하는가?
- pak이 암호화됐는가?
- 한국어 텍스트가 일반적인 `Game.locres`에 들어 있는가?
- Oodle 압축 자산을 실제로 선택 추출할 수 있는가?

### 실제 검증 방법과 결과

- Steam `appmanifest_1623730.acf`에서 Build ID `24181527`과 언어 `koreana`를 확인했다.
- `repak 0.2.3 info/list`로 pak V11, 인덱스 암호화 없음, Oodle 압축, 185,003개 엔트리를 확인했다.
- 두 후보 DataTable과 파트너·패시브·한국어 패키지 경로가 현재 인덱스에 실제로 존재함을 확인했다.
- 필요한 15개 파일만 프로젝트의 무시된 캐시 경로로 선택 추출했다.
- 한국어 `Game.locres`는 37 bytes였고, `L10N/ko` 아래에 한국어 DataTable 오버라이드가 따로 존재했다.

### 잘못된 부분

첫 선택 추출은 `Oodle loader error: Oodle initialization failed previously`로 실패했다.
처음에는 pak 또는 도구 호환성 문제일 가능성도 있었지만 실제 원인은 샌드박스 안에서 repak의 Oodle DLL 자동 다운로드가 막힌 것이었다.

### 수정 요청

repak 0.2.3 소스의 Oodle 로더를 확인해 요구 DLL, 다운로드 위치와 고정 SHA-256을 검증한 뒤 네트워크가 허용된 상태로 선택 추출을 다시 실행했다.

### 최종 결정

- pak 인덱스 탐색과 선택 추출에는 `repak 0.2.3`을 사용한다.
- Oodle DLL은 도구 캐시에만 두고 Git에 커밋하지 않는다.
- 한국어 결합을 `locres` 중심으로 단정하지 않고 `L10N/ko` 패키지 오버라이드를 우선 조사한다.
- DataTable 필드 직렬화는 최신 CUE4Parse와 현재 빌드용 매핑을 별도로 검증한다.

## 2026-07-25 — CUE4Parse 로컬 SDK와 의존성 검증

### 목표

시스템 전역 환경을 바꾸지 않고 반복 가능한 C# 추출기 빌드 경로를 만든다.

### 내가 AI에 준 요청

현재 PC에 .NET SDK가 없는 상태에서 게임 원본을 수정하지 않는 추출기를 만들도록 요청했다.

### AI가 제안한 내용

- .NET SDK를 프로젝트의 무시된 도구 캐시에만 설치한다.
- 최신 CUE4Parse 패키지로 UE 5.1 패키지 로딩을 검증한다.
- NuGet 캐시도 프로젝트의 무시된 캐시로 격리한다.

### 내가 의심하거나 검증한 부분

- 최신 CUE4Parse가 현재 환경에서 빌드되는가?
- 전이 의존성에 알려진 취약점이 남는가?
- 시스템 전역 SDK 설치 없이 재현 가능한가?

### 실제 검증 방법과 결과

- `.cache/dotnet`에 .NET SDK `10.0.302`를 설치했고 시스템 전역 설정은 바꾸지 않았다.
- `CUE4Parse 1.2.2.202607`을 사용해 추출기 restore와 build를 실행했다.
- NuGet 감사 결과 `Microsoft.Bcl.Memory 9.0.0`에 `GHSA-73j8-2gch-69rq`가 보고됨을 확인했다.

### 잘못된 부분

처음 고정한 `Newtonsoft.Json 13.0.3`은 CUE4Parse가 요구하는 최소 버전 `13.0.4`보다 낮아 restore가 실패했다.
또한 CUE4Parse의 전이 의존성만 따르면 취약한 `Microsoft.Bcl.Memory 9.0.0`이 선택됐다.

### 수정 요청

`Newtonsoft.Json 13.0.4`와 취약점 수정 버전인 `Microsoft.Bcl.Memory 10.0.4`를 직접 고정하고 다시 restore/build했다.

### 최종 결정

- 추출기는 `net10.0`과 `CUE4Parse 1.2.2.202607`을 사용한다.
- 로컬 SDK와 NuGet 패키지는 `.cache` 아래에만 두고 Git에서 제외한다.
- 직접 고정한 보안 패키지 버전을 임의로 낮추지 않는다.
- 수정 후 build는 경고 0개, 오류 0개로 통과했다.

## 2026-07-25 — unversioned property 매핑 요구 확인

### 목표

현재 pak에서 `DT_PalMonsterParameter`를 실제로 직렬화하고 3~5종 샘플 추출 가능 여부를 확인한다.

### 내가 의심하거나 검증한 부분

- 현재 pak이 UE 5.1 설정과 CUE4Parse로 마운트되는가?
- 매핑 없이 DataTable 행까지 읽을 수 있는가?
- 공개된 최신 매핑이 설치된 Build ID와 맞는가?

### 실제 검증 방법과 결과

- 게임 실행 파일 문자열에서 `++UE5+Release-5.1`과 `Unreal Engine 5.1.1`을 확인했다.
- `DefaultFileProvider`를 UE 5.1로 초기화하고 `Mount()`를 호출하자 pak 마운트에 성공했다.
- `DT_PalMonsterParameter` 로드 단계에서 `Package has unversioned properties but mapping file is missing` 오류가 발생했다.
- Nexus Mods의 `Mapping101` 파일은 버전 `1.0.1`, 업로드 시각 `2026-07-18`, 파일 ID `17203`으로 확인했다.

### 잘못된 부분

첫 구현에서는 `Initialize()` 뒤에 `Mount()`를 호출하지 않아 자산 키를 찾지 못했다.
현재 CUE4Parse API 소스를 확인한 뒤 명시적 `Mount()`가 필요함을 반영했다.

### 수정 요청

- pak 마운트 수가 0이면 즉시 실패하도록 경계 검사를 추가했다.
- 선택적 `.usmap` 경로를 받아 `FileUsmapTypeMappingsProvider`로 주입하게 했다.

### 최종 결정

- 현재 설치본의 DataTable 직렬화에는 현재 빌드와 호환되는 `.usmap`이 필수다.
- 매핑은 저작권·재배포 조건 때문에 `.cache`에만 두고 커밋하지 않는다.
- `Mapping101`은 날짜와 버전이 유력한 후보일 뿐, CUE4Parse로 실제 행을 읽기 전까지 호환 확정으로 기록하지 않는다.
## 2026-07-25 — Nexus 매핑 다운로드와 현재 빌드 호환 확정

### 목표

로그인이 필요한 최신 매핑을 안전하게 받아 Build ID `24181527`의 unversioned DataTable을 실제로 읽는다.

### 내가 AI에 준 요청

Nexus 로그인을 마쳤으니 설치본 원본을 읽는 작업을 계속 진행하라고 요청했다.

### AI가 제안한 내용

- Nexus의 `Mapping101` 파일만 다운로드한다.
- 게임 설치 폴더가 아니라 Git에서 제외된 `.cache`에 보관한다.
- 압축을 풀기 전에 공개된 해시와 ZIP 내부 경로를 검증한다.
- 매핑 파일을 CUE4Parse에 주입해 현재 pak의 행 직렬화 성공 여부로 호환성을 판정한다.

### 내가 의심하거나 검증한 부분

- 브라우저 자동화가 다운로드 완료 이벤트를 받지 못했는데 파일을 사용해도 되는가?
- 파일이 변조되거나 잘못된 ZIP일 가능성은 없는가?
- 업로드 날짜가 최신이라는 이유만으로 현재 Build ID와 호환된다고 단정한 것은 아닌가?

### 실제 검증 방법과 결과

- 브라우저 다운로드 이벤트는 60초 뒤 타임아웃됐지만 다운로드 폴더에 804,188 bytes 파일이 생성된 것을 확인했다.
- SHA-256 `AD7A6C19D9A15D75E8FA367DB8B453AEC2A5705323EFFC44429E655AB2B27D15`가 Nexus가 연결한 VirusTotal 해시와 일치했다.
- ZIP 내부 경로를 검사한 뒤 `Mappings101.usmap` 한 파일만 `.cache`에 풀었다.
- usmap SHA-256은 `B9B1EF0A5B2FBA657D421F43C31DDA7D3818AADB50E52C1C3215DFE45DB9FB44`였다.
- CUE4Parse가 같은 provider에서 pak 1개를 마운트하고 `DT_PalMonsterParameter` 753행을 정상 직렬화했다.

### 잘못된 부분

브라우저 다운로드 이벤트 타임아웃만 보면 다운로드 실패로 오판할 수 있었다. 또한 최신 업로드라는 메타정보만으로 매핑 호환성을 확정하면 뇌피셜이었다.

### 수정 요청

실제 파일 크기, ZIP 구조, SHA-256과 현재 pak 행 직렬화를 각각 검증한 뒤에만 호환 상태를 갱신했다.

### 최종 결정

- `Mapping101 1.0.1`은 현재 설치본의 MVP 대상 자산에서 호환 확인으로 기록한다.
- ZIP과 usmap은 `.cache`에만 두고 공개 저장소에 커밋하지 않는다.
- 향후 게임 Build ID가 바뀌면 같은 직렬화 검사를 다시 통과해야 한다.

## 2026-07-25 — CUE4Parse API 오해와 텍스처 변환 수정

### 목표

DataTable 조사 명령과 팰 아이콘 PNG 변환을 반복 실행 가능한 C# 명령으로 만든다.

### AI가 제안한 내용

- `table`, `package`, `texture` 진단 명령을 하나의 추출기에 추가한다.
- 아이콘 DataTable의 soft object path를 패키지 경로로 바꿔 `UTexture2D`를 읽는다.
- 디코딩 결과를 SkiaSharp로 PNG 인코딩한다.

### 내가 의심하거나 검증한 부분

- 설치된 CUE4Parse 패키지의 실제 API가 AI가 기억한 예시와 같은가?
- 텍스처 변환이 컴파일만 되는 것이 아니라 실제 128×128 아이콘을 만드는가?
- 출력 경로가 실수로 게임 설치 폴더를 가리킬 수 없는가?

### 실제 검증 방법과 결과

- 모든 변경 뒤 `dotnet build --no-restore`를 실행했다.
- `TextureEncoder.cs`의 현재 소스를 확인해 `CTexture.ToSkBitmap()` 확장 메서드와 `Width`, `Height` 속성을 사용하도록 고쳤다.
- `T_PinkRabbit_icon_normal`을 128×128 PNG로 변환했고 PNG 시그니처와 실제 핑토 이미지를 확인했다.
- 이후 5종 아이콘을 모두 변환해 팰 ID와 그림이 맞는지 눈으로 대조했다.
- 출력 경로가 Palworld 설치 루트 내부면 거부하는 검사를 추가했다.

### 잘못된 부분

- C# list pattern에서 같은 지역 변수명을 재사용해 컴파일 오류 3개를 냈다.
- package export API를 `export.Name.Text`와 컬렉션 `Count` 속성으로 추정해 컴파일 오류 3개를 냈다. 실제 API는 문자열 `Name`과 LINQ `Count()`였다.
- 가장 큰 오류는 `TextureDecoder.Decode()`가 `SKBitmap`을 반환한다고 가정한 것이다. 실제 반환형 `CTexture`는 `IDisposable`이 아니고 `UTexture2D`에도 직접 `SizeX`, `SizeY` 속성이 없어 컴파일 오류 4개가 났다.

### 수정 요청

컴파일러 오류를 기준으로 추측 코드를 버리고 설치된 NuGet 버전과 CUE4Parse 공식 소스의 정확한 시그니처를 확인해 수정했다.

### 최종 결정

- CUE4Parse 관련 코드는 기억이나 예전 예시가 아니라 고정한 패키지 버전의 소스와 컴파일 결과로 검증한다.
- 텍스처 디코딩은 `texture.Decode() -> CTexture.ToSkBitmap() -> PNG` 순서로 고정한다.
- 수정 후 추출기는 경고 0개, 오류 0개로 빌드된다.

## 2026-07-25 — 5종 한국어·거점 효과·아이콘 샘플 결합

### 목표

전체 추출 전에 서로 다른 게임 DataTable 참조를 팰 5종 단위로 묶고, 거점 작업 파트너 효과를 구조화한다.

### AI가 제안한 내용

- 핑토, 캐티위자드, 리오리네, 누름북, 짜리링을 서로 다른 작업 종류의 샘플로 선택한다.
- 팰 기본값, 한국어 이름, 파트너 파라미터, 패시브 정의, 한국어 설명, UI 작업 적성명과 아이콘 매핑을 결합한다.
- 설명문은 화면 표시용으로 렌더링하되 구조화된 수치와 대상 판정의 1차 근거로 쓰지 않는다.

### 내가 의심하거나 검증한 부분

- 파트너 스킬 설명이 일반 `DT_SkillDescText_Common`에 실제로 있는가?
- “다른 거점 팰”, 증가량 `+1`, 중복 불가가 구조화 필드와 일치하는가?
- 파트너 스킬 랭크가 오르면 작업 적성 증가량도 바뀌는가?
- 아이콘 soft object path가 실제 해당 팰 그림으로 이어지는가?

### 실제 검증 방법과 결과

- 일반 스킬 설명 테이블에는 대상 파트너 설명이 없었다. 한국어 텍스트 자산을 역검색해 `DT_PalFirstActivatedInfoText`의 `PAL_FIRST_SPAWN_DESC_{PalId}` 행을 찾았다.
- 작업 적성명은 `DT_UI_Common_Text_Common`의 `COMMON_WORK_SUITABILITY_*` 19행에서 읽었다.
- 다섯 효과 모두 패시브 정의에서 `ToBaseCampPal`, `InvokeInBaseCamp=true`, `IsStackablePartnerSkillBySameTribe=false`였고 파트너 할당에는 `bNotAssignSelf=true`였다.
- 한국어 원문도 “다른 거점 팰”과 “중복 불가”로 구조화 값과 일치했다.
- 파트너 파라미터 배열의 다섯 인덱스에서 작업 적성 증가량은 모두 `1/1/1/1/1`이었다.
- `sample` 명령 결과는 팰 5, 고유 ID 5, 아이콘 5, 거점 효과 5, 검증 오류 0이었다.

### 잘못된 부분

처음에는 파트너 스킬 설명도 이름과 마찬가지로 일반 스킬 설명 테이블에 있을 것으로 예상했다. 그 가정대로 구현했으면 한국어 설명이 비거나 엉뚱한 fallback 데이터가 들어갈 뻔했다.

또한 PowerShell 5의 `ConvertFrom-Json`에 최신 PowerShell 전용 `-AsHashtable` 옵션을 사용하려 해 진단 스크립트가 한 번 실패했다. 이후 `PSObject.Properties`와 C# 내부 검증으로 바꿨다.

### 수정 요청

- 한국어 자산 전체에서 실제 행 키를 역검색해 파트너 전용 설명 테이블을 데이터 맵에 추가했다.

## 2026-07-25 — 작업 필터 전체 감사와 대상 팰 한정 효과 수정

### 목표

파종·채집 필터에서 세크메트가 잘못 노출되는 원인을 찾고, 세크메트 한 건을
숨기는 임시 예외가 아니라 전체 26개 효과의 작업 적용 범위를 다시 검증한다.

### 내가 AI에 준 요청

- 채집·파종을 선택했을 때 세크메트가 나오는 이유를 물었다.
- 세크메트뿐 아니라 전체 효과를 검수하고 패치하라고 했다.

### AI가 제안한 내용

- 두 검색 엔진에서 `workSuitabilityId=null`을 전 작업 와일드카드로 처리하는
  로직을 제거한다.
- 추출기가 원본의 특정 작업 필드와 별도로 효과별
  `applicableWorkSuitabilityIds`를 만들게 한다.
- 대상 팰이 지정된 전체 작업 속도 효과는 대상 팰의 설치본 작업 적성에서
  적용 가능한 작업을 계산하고, 일반 작업 속도 특성만 전 작업으로 분류한다.

### 내가 의심하거나 검증한 부분

- `null`인 효과를 전부 제외하면 장인 기질·초절기교 같은 일반 작업 속도
  특성까지 사라지는 것 아닌가?
- 세크메트 자신의 작업 적성이 아니라 효과 대상인 아누비스의 작업 적성을
  기준으로 해야 하는 것 아닌가?
- 다른 25개 효과에도 대상 팰 한정 `null` 효과나 잘못된 작업 태그가 있는가?

### 실제 검증 방법과 결과

- 26개 효과를 구조 필드 기준으로 전수 분류했다. 특정 작업이 명시된 효과는
  18개, `workSuitabilityId=null`인 효과는 8개였다.
- `null` 8개 중 7개는 표시 가능한 일반 작업 속도 특성이었고, 나머지 1개가
  아누비스만 대상으로 하는 세크메트의 전체 작업 속도 효과였다.
- 설치본 `DT_PalMonsterParameter`의 `Anubis` 행에서 수작업 6, 채굴 6,
  운반 4만 양수이고 파종·채집은 0임을 확인했다.
- 재생성 결과 효과 26개, 적용 가능 작업이 빈 효과 0개, 잘못된 작업 ID 0개,
  생성기 검증 오류 0개였다.
- 브라우저에서 MVP 작업 필터 12종을 전부 클릭했다. 파종·채집은 각각 8개며
  세크메트는 0개였다. 세크메트는 수작업에서 두 효과, 채굴·운반에서 각 한
  효과만 남았다. 나머지 필터별 결과 수도 구조화 데이터 예상값과 일치했다.
- 브라우저 콘솔 warning/error는 0개였다.
- C# 빌드 경고·오류 0, `pnpm lint`, `pnpm typecheck`, 테스트 13개,
  루트·Antigravity 프로덕션 빌드를 통과했다.

### 잘못된 부분

- 기존 검색기는 “특정 작업이 구조 필드에 없음”과 “모든 작업에 적용됨”을
  같은 뜻으로 취급했다. 이 때문에 대상이 아누비스로 제한된 효과도 파종·채집

- 첫 브라우저 QA 스크립트에서 지원되지 않는 `domcontentloaded` 헬퍼를 호출해
  한 번 실패했다. 이미 완료된 탐색은 유지하고 지원되는 DOM snapshot과
  locator API로 전수 검사를 계속했다.
- 샌드박스 안 Vitest는 `spawn EPERM`으로 시작하지 못해 자식 프로세스가
  허용된 환경에서 같은 테스트를 다시 실행했다.

### 수정 요청

- 추출기가 명시 작업, 일반 전 작업 속도, 대상 팰 작업 적성, 소유 팰 작업

- 루트 UI와 Antigravity UI가 동일하게 새 배열만 보고 필터링하게 교체했다.
- 세크메트 대상 효과의 적용 작업 3종과 일반 특성 7개의 전 작업 적용을
  회귀 테스트로 고정했다.
- 생성기와 런타임 데이터 검증에 빈 배열, 알 수 없는 ID, 중복 ID와 명시 작업
  불일치 검사를 추가했다.

### 최종 결정

- `workSuitabilityId=null`은 원본 의미 보존용이며 검색 와일드카드로 쓰지 않는다.
- 검색은 추출 단계에서 근거와 함께 계산한 `applicableWorkSuitabilityIds`만
  사용한다.
- 대상 팰 한정 전체 작업 효과는 현재 설치본의 대상 팰 작업 적성이 바뀌면
  재생성 시 자동으로 따라가게 한다.
